# SEO и доступность strop.su

Проверка проекта завершена 04.10.2026. Изменения находятся в локальном проекте; на внешний хостинг они не опубликованы. Паспортам по указанию заказчика оставлена дата 02.10.2026.

## Диагностика загрузки

Повторная проверка 04.10.2026: опубликованный HTML всё ещё содержит «МИКО», не содержит `<main>` и требует JavaScript. Из 11 файлов CSS/JS четыре не завершили загрузку за 15 секунд. При повторной проверке один загрузился за 408 мс, три снова не завершились за 30 секунд, хотя получили HTTP 200: `07lhk_q6pmm3r.js` (48 071 байт до остановки), `12ys~36e.61lo.js` (68 792 байта), `03~yq9q893hmn.js` (48 257 байт). Это воспроизведённая неполная доставка скриптов из сети проверки, а не ответ 404. Точное место сетевого сбоя — CDN, хостинг или маршрут — без сравнения с адресом проекта Netlify и журналами не установлено.

Локальный сервер запущен на `http://127.0.0.1:3000`. Главная, каталог и категория стропов вернули HTTP 200 с содержимым; все 20 скриптов, найденных на локальной главной, вернули HTTP 200.

Для следующего шага нужны адрес проекта `*.netlify.app`, название/Project ID в Netlify, статус и журнал последнего деплоя, DNS-записи A/AAAA/CNAME и настройки домена/HTTPS. Пароль в переписке не требуется. Не следует публиковать SMTP-пароли и токены из журналов.

При сетевой проверке 02.10.2026 `https://strop.su` отвечал HTTP 200 с сервера Netlify. В HTML размером 10 188 байт отсутствовал `<main>` и был маркер `BAILOUT_TO_CLIENT_SIDE_RENDERING`. Заголовок содержал прежнее название ООО «МИКО». Опубликованная версия ожидала JavaScript для отображения основного содержимого. Если скрипт не загрузился или не выполнился, это могло приводить к пустой странице или бесконечному ожиданию. Такая зависимость подтверждена, но она не доказывает причину каждого сбоя на каждом устройстве.

DNS возвращал IPv4 35.157.26.135 и 63.176.8.218. Работа из одной сети не доказывает доступность из всех сетей и через любой VPN. Название VPN, страна выхода, браузер и точный адрес сбоя не предоставлены; проверка через конкретный VPN не выполнена. В исходном коде ограничения по стране или VPN не обнаружены. Настройки CDN, защиты хостинга и DNS находятся вне локального проекта.

## Как работает продвижение

Поисковая система находит страницы по ссылкам и sitemap, читает и индексирует их, затем выбирает подходящие страницы под запрос пользователя. Отдельные адреса моделей позволяют продвигать конкретный ассортимент. Разметка, title и быстрый HTML помогают интерпретации сайта, но не гарантируют позиции. Также нужны полезные описания, точные характеристики, актуальные цены, информация о доставке, репутация и измерение заявок. См. [руководство Google по поисковой оптимизации](https://developers.google.com/search/docs/fundamentals/seo-starter-guide?hl=ru).

Техническая основа улучшена. Полный вывод о результатах продвижения требует публикации, данных поисковых кабинетов и измерений реальной мобильной скорости. Lighthouse и Core Web Vitals не измерены; оценка «100/100» не заявляется.

## Подключение после регистрации

1. Добавить `https://strop.su` в Яндекс Вебмастер и Google Search Console. Выбрать подтверждение метатегом и скопировать значение `content`.
2. На хостинге установить `YANDEX_SITE_VERIFICATION` и `GOOGLE_SITE_VERIFICATION`, затем пересобрать и опубликовать сайт. Подтвердить права в кабинетах. Шаблон имён переменных: `seo.env.example`. См. [инструкцию Яндекс Вебмастера](https://yandex.ru/support/webmaster/ru/service/rights).
3. Добавить `https://strop.su/sitemap.xml` в оба кабинета, проверить несколько страниц и запросить переобход главной.
4. Создать счётчик Метрики, добавить `NEXT_PUBLIC_YANDEX_METRIKA_ID` и пересобрать сайт. Подготовлены цели `product_open`, `add_to_cart`, `request_sent`; последняя отправляется после успешного ответа API. Учтены [переходы SPA](https://yandex.ru/support/metrica/ru/code/counter-spa-setup). Вебвизор выключен, содержимое форм в цели не передаётся.
5. Проверять запросы, индексирование, ошибки обхода и число заявок. Исправлять исключение важных страниц, затем развивать описания по реальным поисковым запросам.

Аккаунты и подтверждение не настроены: заказчик создаст их позднее. Идентификаторы не выдуманы, счётчик не активен.

## Что нужно для завершения проверки доступности

1. Опубликовать проект на действующем Netlify-сайте. `start-site.cmd` запускает локальную разработку и не публикует сайт.
2. Проверить исходный HTML домена: содержимое и название МПК должны присутствовать до запуска JavaScript. Проверить каталог, модель, sitemap и загрузку ресурсов.
3. Повторить открытие через Wi-Fi, мобильный интернет и проблемный VPN. Записать браузер, страну выхода VPN, время и ошибки Network. Если HTML не приходит, исследовать DNS/CDN/хостинг: React такой сетевой отказ не исправит.
4. При подтверждённом отказе в конкретной сети проверить журналы и правила хостинга. Менять DNS или хостинг следует после воспроизведения. Доступа к управлению хостингом и DNS в этой работе не было.

## Выполненные проверки

Production build и TypeScript прошли. ESLint: ошибок нет, четыре предупреждения о локальных `<img>`. Все 1115 извлечённых ячеек совпали с указанным Excel. Проверены 55 моделей, 337 вариантов длины, 18 исправленных размеров P1, суммы дополнений и тексты заявок. Все 65 проверенных локальных HTTP-адресов вернули 200; неизвестная модель — 404. Проверены HTML, H1, canonical, ссылки, количество моделей категорий и noindex пустых категорий.

Живой браузер в доступных инструментах отсутствует. Клики, мобильная компоновка и работа через VPN интерактивно не проверены. На опубликованном домене обновления ещё не проверялись, поскольку публикация не выполнялась.
